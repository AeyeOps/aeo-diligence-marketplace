# Ingest a diligence target

Run the requested tier, preserve analyst curations, and finish with a dashboard the user can open. In Claude Code this skill is `/code-diligence:aeo-diligence-ingest` from the plugin or `/aeo-diligence-ingest` as a standalone skill; in Codex it is `$aeo-diligence-ingest`.

1. Each target has its own folder, holding its settings file `diligence.local.md` beside its warehouse. Use the folder the user names, or the folder of the warehouse the connected MCP reads. Read its `diligence.local.md`. If it is missing, create it from [the settings template](templates/diligence.example.local.md) using the target and sources the user supplied, with every storage path inside that folder. Ask only for required source or storage choices that are still unknown. Settings name the environment variable that holds a credential, never the credential itself.

   AWS Inspector security findings are optional. When the target runs on AWS and neither `sources.aws_inspector` nor a supplied `dashboard.security_chart_path` is set, ask whether to include them and say what that takes: an AWS CLI profile on this machine that can read Inspector findings (`inspector2:ListFindings`) in the target's account and region; the name prefixes of the target's resources when the account also holds other workloads; and any folder of saved Inspector snapshots for history. Inspector deletes closed findings 30 days after they close, so months before the first saved snapshot or read cannot be rebuilt, and history grows with each full refresh. Settings name the profile, never its keys. If the profile is missing or access is denied, the refresh records an `aws-inspector` failure on Health; tell the user and continue.
   Keep resource and fix-availability selections in the target settings. `sources.aws_inspector.fix_available` accepts `YES`, `NO`, and `PARTIAL`; an empty or omitted list applies no fix-availability filter. Use the user's selected population for this target.
2. If the user has not chosen a tier, ask whether they want quick (git history and available lightweight tools) or full (also the available deep analyzers and enabled GitHub data). Runtime depends on repository size and installed tools.
   Before ingest, use [host installation guidance](references/tool-prerequisites.md#choose-the-installation-environment) to select tools for the execution environment's OS and architecture. Follow [prerequisite coverage](references/tool-prerequisites.md#explain-and-resolve-coverage-gaps): verify the requested tier's tools and the native warehouse MCP, explain every confirmed gap and its consequence, recommend how to close it, and establish whether the user wants the gap closed or accepts reduced coverage. Existing installation or repair authorization carries forward; act on it without asking again.
3. Set `heuristics.fte_inference: false` in the target's settings so assessment does not decide employment or automation labels before the user interview. Resolve the plugin root, the `plugins/code-diligence` folder that holds the runtime: `CLAUDE_PLUGIN_ROOT` in a plugin install, otherwise `CODE_DILIGENCE_ROOT`. If neither is set, tell the user to set `CODE_DILIGENCE_ROOT` to that folder of their aeo-diligence-marketplace checkout. Start every runtime command through `$PLUGIN_ROOT/bin/run`, which runs it in the plugin's own environment whatever environment the calling shell selects. Then run:

   ```sh
   "$PLUGIN_ROOT/bin/run" code-diligence ingest "$SETTINGS_PATH" --quick
   ```

   Substitute `--full` when requested. GitHub-enabled targets discover and clone the configured organizations. Local targets read existing checkouts under `storage.repo_clone_root`. On the full tier, a local checkout's GitHub platform data comes from its `origin` repository.
4. Inspect the CLI result, curation paths and review counts. A nonzero exit is a failed ingest; report the actual error. For newly discovered tool failures, follow the same coverage-gap procedure before declaring completion. Tool failures recorded in the warehouse remain visible on Health; a zero exit is not proof that every requested analyzer ran.
5. After assessing the repositories, conduct the [contributor classification interview](references/contributor-interview.md). Present the distinct identities and ask the user how to classify them, carrying forward answers already given. Save the answers in this target's curation files and apply them before interpreting People metrics. Repository-specific classifications belong to the consuming target, not the shared skills or classifier.
6. Before narration, prepare Security chart data using the `aeo-diligence-dashboard` skill's `references/security-chart.md`. Honor the requested interval and range, and use `dashboard.security_chart_path` when configured. Pass the prepared target document as `metric_context` for `product/security_findings`; this card is not narrated from the six-month cache. Do not manufacture missing counts or infer a zero baseline from missing history.

   If this session's warehouse MCP is connected to the target, use the runtime's native subagent tool to run a narrator for each card in `axes_taxonomy`: the plugin's `diligence-narrator` agent, or without the plugin a subagent briefed with `agents/diligence-narrator.md` under the plugin root and limited to the warehouse tools. Read the `humanizer` skill and include its instructions in a standalone narrator's brief; the plugin agent preloads it. Pass target ID, warehouse path, axis, section key and tier. Supply `metric_context` from the `aeo-diligence-axes` skill's matching `references/people.md`, `references/product.md`, or `references/process.md` and that card's SQL: the query function its `aeo-diligence-dashboard` page under `templates/observable/src/targets` imports from that skill's `templates/observable/src/data/metrics.js`, or the query written in the page. The CLI has closed its database connection before agents write. Generate working-pattern prose only when `heuristics.allow_working_pattern_card` is true. For an unavailable or misdirected MCP, follow the `aeo-diligence-ask` skill's `references/asker-boundary.md` and carry out authorized recovery before reporting a remaining blocker. Narration must respect the user's model/network choice; do not claim it ran when it did not.
   Include `dashboard.contributor_labels` from the target settings in each narrator's `metric_context`. These canonical-email labels keep person names consistent with the dashboard without changing collected identities.
7. Apply the `aeo-diligence-dashboard` skill, including target, curation directory and privacy setting. Report the output path, preview URL, and any missing data sources.

Use [pipeline stages](references/pipeline-stages.md) for data ownership and [tool prerequisites](references/tool-prerequisites.md) for optional analyzers. Keep these references aligned when a real run reveals a changed command or tool format.
